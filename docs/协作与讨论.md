# 协作与讨论

本项目把不同类型的交流分开处理，让信息容易找到，也让维护者能够持续跟进。

## 先选择入口

| 你想做什么 | 推荐入口 | 说明 |
| --- | --- | --- |
| 分享使用经验、比较方案、讨论审美或未成形的想法 | [Discussions](https://github.com/Chocologician/codex-ppt-refined-skill/discussions) | 适合开放交流，不要求已经形成明确任务。 |
| 报告可以复现的问题 | [问题反馈](../.github/ISSUE_TEMPLATE/问题反馈.yml) | 提供环境、步骤、预期结果和实际结果。 |
| 提出新能力或改变默认行为 | [功能提案](../.github/ISSUE_TEMPLATE/功能提案.yml) | 先说明需求、范围、替代方案和验证方式。 |
| 提交已经完成的修改 | [Pull Request](https://github.com/Chocologician/codex-ppt-refined-skill/pulls) | 说明问题、改动、来源、兼容性和验证结果。 |
| 讨论安全问题或敏感信息 | [安全说明](../SECURITY.md) | 不要在公开 Issue 或 Discussion 中发布凭据和私人材料。 |

## Discussions 分类

仓库已启用 Discussions，按以下分类交流：

- **公告**：版本、兼容性和维护安排，只由维护者发布；
- **问答**：使用问题、环境差异和排障经验；
- **创意与提案**：新工作流、版式、动画或工具想法；
- **展示与案例**：公开或合成材料的作品与复盘；
- **开放交流**：项目方向、协作方式和社区建议。
- **社区投票**：收集对方案和优先级的意见，作为维护决策的参考。

提问前请先搜索已有内容。一个讨论应尽量围绕一个主题；如果已经形成清晰的实现任务，再由参与者将它转成 Issue 或 Pull Request。

## Issue 处理方式

1. 先确认问题属于本项目范围，并搜索已有 Issue 和 Discussion。
2. 使用问题反馈或功能提案模板，写清环境、事实、预期和验证条件。
3. 维护者会判断是否需要补充信息、标记优先级或转入讨论。
4. 已确认的问题才进入实现排期；长期没有足够信息的问题可以暂缓或关闭，并说明原因。

Issue 用于记录可执行的任务，不用于索取私人定制、发布凭据或粘贴未公开材料。

## Pull Request 处理方式

1. 从 `main` 创建分支或复刻仓库，分支名称简洁说明意图，例如 `docs/contributing-guide`、`fix/plan-validation`。
2. 一个 Pull Request 聚焦一个主要变化。大改动先在 Discussion 或 Issue 中讨论范围。
3. 提交标题使用 `修复：`、`新增：`、`文档：`、`示例：` 或 `重构：` 等清晰前缀。
4. 描述中写明关联任务、改动范围、来源和许可证、测试结果及未验证部分。
5. CI 通过后等待维护者评审；视觉或动画改动还需要提供同条件前后对比。
6. 维护者可以提出修改、合并、关闭或建议拆分。合并后由维护者整理变更记录，必要时进入下一个版本。

提交前请阅读[贡献指南](../CONTRIBUTING.md)、[维护约定](../GOVERNANCE.md)和[行为准则](../CODE_OF_CONDUCT.md)。
